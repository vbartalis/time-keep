# History Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A History screen on the PC: every batch newest first with its changes, and any batch, or chosen changes, undone and redone in one step.

**Architecture:** The core gains `redo`, which undoes the standing changes that revert the named ones, labelled `Redo …`. Server helpers in `src/lib/server/screens/history.ts` (unit-tested) describe a change in words, give a batch's state, and read the page's query and posted ids. The `/history` route lists `history.list` 50 to a page and posts to its own `?/undo` and `?/redo` actions, redirecting back with the strip.

**Tech Stack:** SvelteKit 3.1 (adapter-node, `#lib` imports, Svelte 5 runes), Drizzle over better-sqlite3, zod, Tailwind, shadcn-svelte owned in the repo, Lucide icons, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-19-history-design.md`

## Global Constraints

- Every screen action is one core call (`core.undo` or `core.redo`); no rule is enforced in a screen (`docs/core.md`). History rows are only read; undo and redo only add batches.
- Forms work without JavaScript; `use:enhance` enhances them. No browser dialogs, no confirmation step.
- A successful action redirects 303 to the page it was posted from (`/history` plus its `before`) through `done(core, cookies, r, back)`; the strip shows there and `/undo` returns there (`safeBack`).
- Limits: 50 batches to a page (the screen asks for 51); at most 100 changes shown per batch, none tickable beyond that; 1 to 1000 ticked changes; field text cut at 80 characters with "…".
- Copy (exact): "Nothing recorded yet.", "Older", "Newest", "1 change" / "<n> changes", "Undone", "Partly undone, <k> of <n>", "Undo", "Redo", "Undo selected changes", "Redo selected changes", "Select at least one change.", "Select at most 1000 changes.", "and <n> more; undo or redo the whole batch.", verbs Created / Changed / Archived / Unarchived / Deleted, "none", "(unknown)", "running", chips "Agent" / "System"; core: "That batch is not undone.", "That change is not undone.", labels `Redo "<label>"`, `Redo 1 change`, `Redo <n> changes`.
- Formats: 24-hour `HH:mm`, `YYYY-MM-DD`, English. The time card world (`DESIGN.md`): violet only for live, primary or focus; red only for irregular or destructive; in-page links in ink, underlined; rules, not boxes.
- Browser tests: `npm run test:e2e`, phone (Pixel 7) and PC (1440×900) projects, one seeded user per project.
- Never run docker; never git push. Conventional Commits, no scope, no AI attribution.

## Review Focus

1. **A redo after the record changed again** (undo "Rename customer", rename it by hand, then Redo) is the core's refusal naming the later batch, nothing written — Task 1.
2. **A batch button posted with ticked boxes** uses the batch alone; ticked ids on another batch are ignored, not undone with it — Task 3.
3. **A forged or foreign id** posted as `batchId` or `changeId`, or a `before` that is not the user's, is the core's "Not found." on the page (or a redirect to `/history` for `before`), never a 500 — Tasks 2, 3.
4. **Values that are not text** in a change's JSON (numbers, null, booleans, a template's `durationMinutes`) print readably, never "[object Object]" or "undefined" — Task 2.
5. **Exactly 50 batches** show no Older link; 51 show it, and Older lists the 51st — Tasks 3, 4.

### Task 1: `core.redo`

**Files:**
- Modify: `src/lib/server/core/history.ts` (`UndoneBy` gains `changeId`), `src/lib/server/core/undo.ts` (`redo`, `redoLabel`), `src/lib/server/core/index.ts` (`BatchCore.redo`, `Core.redo`), `docs/core.md` (Undo › Redo)
- Test: `src/lib/server/core/undo.test.ts` (extend)

**Interfaces:**
- Produces: `core.redo(input: { batchId: string } | { changeIds: string[] }): Result<{ reverted: string[] }>`, on `Core` and `BatchCore`; `reverted` lists the original change ids redone. `UndoneBy = { batchId: string; changeId: string; createdAt: number }` (the standing reverting change).
- `redo(w, input)`: same input schema as `undo`; resolve the named changes (unknown or foreign → `not_found`, "Not found."); with `undoneBy`, keep the undone ones; `{ batchId }` with none undone → `conflict` "That batch is not undone."; `{ changeIds }` with any standing → `conflict` "That change is not undone."; then run `undo`'s change loop on the reverting change ids, so every other refusal is undo's. Return the original ids.
- `redoLabel(input, originalLabel?)`: `Redo "<label>"` / `Redo 1 change` / `Redo <n> changes`; wired in `index.ts` the way `undoLabel` is.

- [ ] **Step 1: Failing tests** in `undo.test.ts`, a `describe('redo')`:
  - redo of an undone rename batch: the name is back, the new batch's label is `Redo "<label>"`, `reverted` equals the original change ids, `listHistory` shows the original batch `undone: false`.
  - chosen changes: undo a two-change batch, redo one change id → that one stands, the other stays undone; label `Redo 1 change`.
  - partly undone batch (one of two undone): `{ batchId }` redoes only that one.
  - refused: `{ batchId }` of a standing batch → `conflict` "That batch is not undone."; `{ changeIds }` with a standing id → `conflict` "That change is not undone."; both write nothing (`counts()` unchanged).
  - refused after a later change: undo a rename, rename again, redo → `conflict` whose message names the later batch; nothing written.
  - alternation: undo, redo, then `undo({ batchId: <redo batch> })` → the change is undone again.
  - unknown and another user's ids → `not_found`; `{ changeIds: [] }` → `invalid`.
  - create a customer, undo the create, redo it: the redo batch has one `create` change and the row is back (never a batch with no change).

### Task 2: History helpers

**Files:**
- Create: `src/lib/server/screens/history.ts`
- Test: `src/lib/server/screens/history.test.ts`

**Interfaces:**
- Consumes: `HistoryBatch`, `HistoryChange`, `Core` (core); `localParts`, `formatTime`, `formatDate`.
- Produces:
  - `type Names = { customers: Map<string, string>; projects: Map<string, { name: string; customerName: string }>; activities: Map<string, string>; locations: Map<string, string> }` and `namesFrom(core: Core): Names` (every list with `includeArchived: true`).
  - `type ChangeLine = { id: string; verb: 'Created' | 'Changed' | 'Archived' | 'Unarchived' | 'Deleted'; subject: string; fields: string[]; undone: boolean }` and `describeChange(change: HistoryChange, names: Names): ChangeLine`.
    - Row keys are camelCase (`startAt`, `archivedAt`, `projectId` …). The row named is `after`, or `before` when `after` is null.
    - Subject per entity: entry "Entry <YYYY-MM-DD HH:mm in startZone>–<HH:mm in endZone | running>, <customer> › <project>"; customer "Customer <name>"; project "Project <customer> › <name>" (customer from `names` by `customerId`); activity, location "Activity <name>", "Location <name>"; template "Template <name>". A missing id → "(unknown)".
    - Verb from `op`; an `update` whose only differing non-hidden key is `archivedAt` → Archived (null → set) or Unarchived (set → null), no fields.
    - Fields (update only), in this order, only those that differ: entry Project, Activity, Location, Start, End, Reference, Description; project Name, Customer; customer/activity/location Name; template Name, Customer, Project, Activity, Location, Start (`startTime`), End (`endTime`), Duration (`durationMinutes`, as `h:mm`), Time zone, Reference, Description; then "Archived: no → yes" / "yes → no" when `archivedAt` differs with other fields. Each `"<Field>: <old> → <new>"`; null or blank → "none"; ids → names; each side cut to 80 characters with "…". Hidden: `id`, `userId`, `version`, `createdAt`, `updatedAt`, `nameKey`.
    - Entry Start/End: one line each, shown when the instant or the zone differs; each side `YYYY-MM-DD HH:mm` in its own zone, followed by ` <zone>` on both sides when the zones differ; an end that is null reads "running".
  - `type BatchState = { state: 'standing' | 'undone' | 'partly'; undone: number; total: number }` and `batchState(batch: HistoryBatch): BatchState`.
  - `dayHeading(at: number, zone: string): string` — `"YYYY-MM-DD, <Weekday>"` (English weekday name).
  - `readChangeIds(form: FormData): { ids: string[]; error: string | null }` — every posted `changeId`, deduped; none → "Select at least one change."; more than 1000 → "Select at most 1000 changes.".
  - `historyPath(before: string | null): string` — `/history` or `/history?before=<encoded id>`.
- [ ] **Step 1: Failing tests** in `history.test.ts`: each op and entity's subject; an entry update changing project and description (names, "none" for a cleared description); a zone-only start change (`2026-10-07 09:00 Europe/Budapest → 2026-10-07 08:00 Europe/London`); a running entry's subject; an archive undone (op `update`, only `archivedAt` set → null) reads Unarchived with no fields; a project rename with archiving reads Changed with "Archived: no → yes"; an unknown project id → "(unknown)"; a 100-character description cut at 80 with "…"; bookkeeping keys never appear; a template's `durationMinutes` 90 → "1:30" and null → "none"; `batchState` for 0, 1 and all of 3 undone; `dayHeading(…, 'Europe/Budapest')` for 2026-10-19 → "2026-10-19, Monday"; `readChangeIds` none, duplicates, 1001.
- [ ] **Step 2: Run** `npx vitest run src/lib/server/screens/history.test.ts` — FAIL.

### Task 3: The History screen

**Files:**
- Create: `src/routes/(app)/history/+page.server.ts`, `+page.svelte`; components under `src/lib/components/history/` (builder's split)
- Modify: `src/routes/(app)/+layout.svelte` (rail item)

**Interfaces:**
- Consumes: Task 1's `core.redo`; Task 2's helpers; `zoneFor`, `takeFlash`, `done`, `safeBack`, `formatTime`; `UndoStrip`.
- `load`: zone as Today; `before = url.searchParams.get('before')`; `history.list({ before, limit: 51 })`; `not_found` → `redirect(303, '/history')`; `older` = the 50th batch's id when 51 came back, else null; batches sliced to 50 and grouped by `dayHeading`; each batch `{ id, time: formatTime, label, actor, count, state: batchState, changes: first 100 described, more: count − 100 when over, tickable: count ≤ 100 }`; `newest = before !== null`; `flash`; `back = historyPath(before)`.
- Actions `undo` and `redo` (same shape, calling `core.undo` / `core.redo`): `back = safeBack(form back)`. A posted `batchId` wins: `{ batchId }`, ticked ids ignored (Review Focus 2). Else `readChangeIds`; error → `fail(400, { error })`. Ok → `done(core, cookies, r, back)`. Refused → `fail(400, { error: r.error.message, selected: ids, open: [batch ids holding them] })`.
- UI per the spec: one `POST` form around the list with a hidden `back`; above the list "Undo selected changes" and "Redo selected changes" (`formaction="?/undo"` / `"?/redo"`), with JavaScript a count line and both disabled at none; the strip; a refusal as the red-bordered alert strip above the list, ticks kept and their batches open; day headings; batch rows (punched time, label, Agent/System chip, the `<details>` count disclosure, the state, outline Undo when any change stands and Redo when any is undone, each `name="batchId" value=<id>` with its `formaction`); change lines (checkbox `name="changeId"` when tickable, the verb, the subject, field lines, "Undone" muted); "and <n> more; undo or redo the whole batch."; Older (`historyPath(older)`) and Newest (`/history`) links; "Nothing recorded yet.". Undone rows muted.
- Rail: History (`@lucide/svelte/icons/history`) after Setup; not in the phone bar; current on `/(app)/history`.
